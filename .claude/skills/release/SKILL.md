# Release and publishing

Moved out of the root `CLAUDE.md`.

## Commands

| Task | Command |
|------|---------|
| Publish a loader/SDK update (no app release) | `gh workflow run publish-loader.yml -f notes="what changed"` (the signing key is a repo secret; `scripts/publish_loader.sh` is what it runs). **If the run's last step fails, the channel is already live and only the stamp is missing** — read `loader.manifest.json` off the `loader` release, set `data/loader_version.json` to its `loader_version`, take `data/changelog.json` from the `changelog` release, and commit both, or main will claim an older loader than users are served |
| Build PyInstaller sidecar | `python scripts/build-sidecar.py` (CI replicates this inline in `.github/workflows/release.yml` — keep both in sync) |
| Bump versions for release | `python scripts/bump-version.py patch --summary "..." --highlight "..." [--highlight "..."]` (or `minor`/`major`/explicit `0.1.12`) — updates all 5 version files AND writes the release note into the same commit (through `add_loader_changelog.py`: replaces a re-run, trims the feed to the 50 the client shows, validates through the client parser). Refused without a note, because CI fails (and the release gate refuses the tag) when the package version has none. `release.yml` uploads the feed from main and dispatches `publish-cli.yml` after publishing; no manual `publish_changelog.sh` needed |

## Notes

**Updater + signing.** Tauri updater feed is `https://github.com/Ovilli/RavenswatchModManager/releases/latest/download/latest.json`, assembled by the `publish-updater-manifest` job in `.github/workflows/release.yml` from `.sig` files produced by `pnpm tauri build`. Pubkey embedded in `tauri.conf.json`; signing private key lives in `TAURI_SIGNING_PRIVATE_KEY` repo secret. The job is skipped when `vars.HAS_UPDATER_SIGNING != 'true'`, in which case releases ship without auto-update support.

**Version sources.** Five files must move in lockstep on every release: `apps/desktop/src-tauri/tauri.conf.json`, `apps/desktop/src-tauri/Cargo.toml`, `apps/desktop/src-tauri/Cargo.lock` (the `rsmm-desktop` entry), `apps/desktop/package.json`, and `pyproject.toml` (the CLI, which ships as the sidecar). Root `package.json` stays at `0.1.0`. Use `scripts/bump-version.py` to keep them aligned; its `--summary`/`--highlight` put the matching `data/changelog.json` entry in the same commit — the desktop app shows it once in a "What's new" dialog after the updater restarts the user into the new build, and a release with no entry silently shows nothing.

**Release notes ship out of band, like the loader and the pattern DB.** `data/changelog.json` is the single source: the desktop bundle imports it as the offline fallback (`apps/desktop/src/lib/changelog.ts`), `build-sidecar.py` bundles it for `rsmm changelog`, and `scripts/publish_changelog.sh` uploads that exact file to the rolling `changelog` GitHub release — so notes cannot drift between the three. This exists because notes compiled into the app can only reach a user by shipping a build, which is backwards for the thing most in need of announcing: a loader/SDK fix that reaches users through `update-loader` with no app release at all. `rsmm.engine.changelog_feed` degrades fetch → cache (6 h TTL) → bundled copy → `unavailable`, so it is cheap to call every launch and works offline. Unsigned **by design** — display text, never code, never written where the game or loader reads — so the trust model is bounds instead of signatures: every field is type-checked, length-capped and control-character stripped (an ANSI escape in a highlight would repaint the terminal rendering it), and entry/highlight counts are capped. The publish script re-runs the client parser and **refuses to publish if any entry would be dropped**, because a silently-dropped entry is a note nobody will ever see. The dialog also clamps to the running app version: the feed routinely describes a release newer than the binary reading it.

**Release flow.** Push the bump commit to `main` and let CI go green FIRST: the release `gate` job waits for the CI run on the tagged commit and refuses the release unless every job except the external-link check passed (v5.9.10 shipped from a red commit before this). A tag on a commit that never went through CI on `main` is refused. Push a `v*` tag → `.github/workflows/release.yml` builds matrix (`ubuntu-22.04` → `.deb` only, `ubuntu-24.04` → AppImage only, `windows-latest` — macOS support dropped; Windows + Linux only. The AppImage bundles its own WebKitGTK and 22.04's made it crawl, so it needs glibc 2.39; `update_env.rs` refuses migration/self-update below that), each leg uploads bundles + `.sig` files to a draft GH release, then `publish-updater-manifest` assembles `latest.json`, then `finalize-release` flips the draft to published. Windows leg uses `shell: pwsh` (not bash) because Git Bash's `/usr/bin/link` shadows MSVC's `link.exe` and breaks Rust builds.

**Loader DLL bundling gotcha.** The Windows CI step builds `winhttp.dll` via `src\loader\build.bat` with `continue-on-error: true`, then PyInstaller bundles `dist/winhttp.dll` if it exists. If `build.bat` writes to the wrong path (it did — fixed in 0.1.11), the build "succeeds" but the DLL is missing from every released sidecar and `rsmm doctor` reports "loader DLL not built" on every user install. Always verify `dist/winhttp.dll` exists after the Windows leg.
