# CLAUDE.md — src/rsmm/engine/

Moved out of the root `CLAUDE.md` so it loads only when working under this directory. Root-level rules still apply.

**Sound banks are the one asset family NOT in `asset_map.json`.** Everything else is loaded through `UsedRscList.ot`, and `asset_map.json` is derived from that list — but the engine loads `Audio/<Name>.bank` by path, so those 16 files never appear in the manifest and every `dec2enc` lookup misses. `apply_mods.resolve_audio_bank()` handles them by ciphering the plaintext path straight through (the `!` directory-collapse rule that complicates normal cooked paths does not apply at that depth: `Audio/Music.bank` → `Wwtdr\Hwvdb.agzm`), and it is wired into `resolve_special` so overriding a bank works like any other asset. The mirroring script needs the same special case — `extract_uncooked.audio_pairs()` lists the cooked audio dir and deciphers each name back, because a CSV-only walk mirrors zero audio. Only the bankset descriptor (`Audio/DarkTales.bankset.FModEventProject.gen`) IS in the map, so `audio_pairs` skips it. Banks are containers: `scripts/extract_audio.py` walks the embedded FSB5 sub-banks (mode 15 Vorbis, setup headers stripped by FMOD and rebuilt by `python-fsb5` — plain ffmpeg cannot read them) and writes one file per sample.

**`*.UsedRscCache.ot` is the second family outside `asset_map.json`, and it is load-bearing.** A definition's resource cache is a plaintext preload manifest sitting beside it — one line per resource, `<Root>|<Decoded\\Path>|<oCClass>` — holding that definition's full transitive dependency closure (the Dark Hills start tile: 784 lines). The engine finds it **by convention, never through `UsedRscList.ot`**: `sub_140311110` appends the literal `.UsedRscCache.ot` to the resource name and applies the usual `\\`→`!` collapse. So none of the 575 shipped caches has a manifest record, none is in `asset_map.json`, and `extract_uncooked.py` mirrored zero of them until `cache_pairs()` was added — the same blind spot as the sound banks. **237 of 237 tiledefs have one, no exceptions** (also 105 hero/enemy `entity`, 81 `enemydef`, … — but 0 of 370 levels and 0 of 733 scenery props). Two failure modes, both hit in-game: a new tiledef with *no* cache preloads nothing, so it is registered, never placed, and reports nothing — that, not the mapdef pool, is why POIs never appeared; and a *stale* cache (a `replace_base` edit reaching assets the cache never listed) leaves a null in the preloaded pointer vector, which the teardown loop at `0x140476f60` destroys without a null check, faulting at `0x1401273b6` reading address 0 with no connection to the real mistake. **It gates at two levels**: the mapdef has a cache of its own listing its pool's tiledefs ONE FOR ONE (Dark Hills: 77 pool entries, 77 `|oCDtTileDefinition` lines), so a tile appended to the pool but absent from the map's cache is never loaded and never placed — fixing only the per-tile caches left the POI invisible for another playtest. The invariant to hold is `pool == map cache tiledef lines`. `rsmm.engine.rsc_cache` builds them, append-only on purpose (a surplus line wastes a preload; a missing one crashes the game), and `_merge_rsc_cache` unions them across mods for the same reason `_merge_map_pool` exists. Two rules: a cache must **not** be registered in `UsedRscList.ot` (`plan_apply` skips them), and anything asking "does the game ship this path" must exempt them, because `is_vanilla_encoded` is `asset_map`-backed and answers False for every shipped cache. ⚠ `data/symbols.json` calls the destroy thunk at `0x1401273b0` `NamedEvent_Delete`; it has **358 callers** and is the generic `destroy(obj)` vtable thunk — the name is not evidence a crash involves named events.

**A cooked file is an object GRAPH, and the graph is owned by a poly-pointer vector. Writing bytes into the stream does not put an object in the file.** Every cooked container ends with a trailer holding `u32 count` + `count` sub-object ids, right after the trailer's nested `MARK_BEGIN` and class index (`data/symbols.json::Serializer_ReadPolyPtrVector` states the encoding). A record that is present in the stream but absent from that vector is an **ORPHAN**: it deserializes, it is byte-stable, it round-trips, it passes every cache/reference/1:1 check — and the engine never instantiates it. Nothing logs, nothing crashes, and the result is a mod that is provably "installed" and does nothing.

This has now cost two separate features, one level apart, and it is the same rule both times:

* **Entities** — `entity_append.append_components` grew section 0 and left the vector alone, so every appended component was an orphan. That is the whole of "spliced records are inert", and it silently killed the INHERIT+OVERRIDE half of the POI marker/interaction. Fixed 2026-09-06 (`component_vector` / `validate_layout`); ★ proven in-game the next playtest — icons drew and the interaction ran end to end.
* **Levels** — `level_placements.add_placement` grew the stream and the section length and left the vector alone, so a `places =` object was an orphan. The tile measured `6 ours (6 built)`, its level resource resolved, 30 swapped objects rendered, and the one ADDED object — carrying the mesh, the icon and the interaction — was never instantiated. Fixed 2026-09-08 (`_object_vector`, called from `add_placement`). ⚠ NOT yet proven in-game.

Where it lives: entities put the vector in the trailer SECTION (`cf.sections[-1]`); levels have only two sections and put it at the **last `MARK_BEGIN` in the whole stream**, inside a literal. In both, the ids are a contiguous `0..n-1` identity prefix — verified `4699/4699` shipped entities and `390/390` shipped levels — which is what makes the append trivial: a new object is always id `count`, wherever in the stream it was inserted. Both walks fail CLOSED (raise, never guess), and `tests/test_level_placements.py` asserts the corpus invariant so a game patch that moves the vector breaks loudly instead of silently writing orphans again. **If you add an object to any cooked container, grow its vector, and prove it by counting objects before and after — a decoder that scans for records will happily read an orphan back and tell you it worked.**

**A mod-ADDED file has no original, and must never be backed up as one.** `plan_apply` returns a `synthesized` set — every encoded path that reached tier 3, i.e. `dec2enc` AND `resolve_special` both declined it, so the game ships nothing there. Those paths take `apply_one`'s `mod_added` branch, which records an empty `orig_sha256` and deletes any stale `.rsmm.bak`, and `restore_one` decides on `orig_sha` rather than on the mere existence of a backup. Without both halves the failure is not cosmetic: the apply transaction snapshots `dest` before overwriting it so a failed batch can roll back, so a mod-added file DOES acquire a `.rsmm.bak` holding *generated* bytes — and `restore --all` then put the mod's own file back and kept it installed. Measured 2026-09-07 on the shrine's mod-owned level. Uninstalling the manager is supposed to leave the game as it was found. `is_vanilla_encoded` still guards the other direction, and the 575 shipped resource caches never reach this path (they resolve at tier 1/2, so they are not `synthesized`).
**Read vanilla bytes through `rsmm.engine.corpus`, never a `data/uncooked` path.** The mirror is gitignored and never bundled, so a player's machine does not have it; `corpus.read/exists/rels/files/stems` answer from the mirror OR the game install (pristine `.rsmm.bak` first). Measured 2026-09-23: with the mirror moved aside, 34 of the repo mods' 42 content blocks failed and the item clone silently fell back to a legacy manifest. The mirror's derived files (`*.json`, `*.glb`, texture `.png`s) have no install twin — read the cooked `.gen` and decode it. `tests/test_corpus_fallback.py` fails on a new `DATA_DIR / "uncooked"` in a kind module, and (with an install present) checks every kind builds identical bytes from both stores; the `install_only` fixture in `tests/conftest.py` hides the mirror for any test.

**Path resolution in frozen mode.** `src/rsmm/engine/paths.py::_find_repo_root` resolves `REPO_ROOT` to PyInstaller's `_MEIPASS` when `sys.frozen` is set. Anything bundled in `build-sidecar.py`'s `add_data_args` is reachable at the same relative path it had in source; anything not bundled is silently missing at runtime. `DEFAULT_GAME_DIR` and `MODS_DIR` are PEP 562 lazy attrs — importing `rsmm.engine.paths` does *not* trigger the disk scan for Ravenswatch (slow on Windows with network drives).

**Re-invoking the CLI from itself uses `self_cmd()`** (`engine/paths.py`). In a frozen bundle `sys.executable` IS rsmm; in source mode it's the Python interpreter + the wrapper script. Never hardcode the entry point.
