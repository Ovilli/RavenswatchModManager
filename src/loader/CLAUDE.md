# CLAUDE.md — src/loader/

Moved out of the root `CLAUDE.md` so it loads only when working under this directory. Root-level rules still apply.

**Installing a detour is one function, not nine.** `src/loader/include/hook_util.h` (`rsmm::hook_install` by pattern name, `hook_install_at` by address, `resolve_checked` for call-only targets, `hook_remove`) is the only path to `MH_CreateHook`. Nine `hook_*.cpp` files used to hand-roll resolve→verify→create→enable and had drifted: only two checked that the target is a **function entry**, several skipped `fn_verify`, and some ignored `MH_EnableHook` failures. Two invariants it enforces, both of which were being violated in shipped code:

1. **`fn_verify` is not an entry-point check.** It proves the recorded bytes are at the address — which a *mid-function* match also does, because a pattern from an older build keeps matching after the routine is merged into a larger one. Only `.pdata` knows where functions begin, so `fn_is_function_start()` (binary search over the module's exception table) gates every install. A detour on a non-entry-point does not intercept a call, it **corrupts** the function it lands in, and the crash surfaces somewhere unrelated much later. The analytics firehose — armed by default on every install — was detouring 0x8d0 bytes inside an unrelated function; `hook_skins.cpp`'s five targets were wrong the same way (one "vector grow" was an aligned-array *deallocator*), and were relocated on 2026-08-09 — it resolves through `Sym::` now. No `FUN_<addr>` literals remain: `hook_skills.cpp` was relocated to `Sym::HeroDef_Deserialize` and `hook_spawn.cpp` was deleted on 2026-09-17 (its address disassembled mid-function on this build, and the instantiator it was hunting was found by the tile-spawn RE instead).
2. **Never resolve by a `"FUN_<addr>"` literal.** That is an address from whatever build the line was written against. The pattern DB keeps such names alive as legacy aliases, so they resolve *and* verify, and land wherever the old bytes now match. Use `Sym::<Name>_Pattern`; add a symbol to `data/symbols.json` if none exists. `tests/test_loader_hook_hygiene.py` gates both rules in CI (no game exe needed) with a shrink-only allowlist; `scripts/verify_symbol_resolve.py` additionally reports where each remaining literal actually lands.

Mod-supplied addresses (`rsmm.hook` → `hook_lua.cpp`) get `EntryCheck::Warn` instead of a refusal: x64 may legitimately omit a true leaf from `.pdata`, and the mod author owns that risk. `hook_lua` keeps its own create/enable sequence because it must set the slot's `installed` flag *between* the two calls — the other order let the game enter a detour while the flag was false, and the hooked function silently did nothing on its first call.

**Demoting a symbol is real in two places, and both are now closed.** `status` used to be cosmetic: the C++/Lua codegen did not filter by it, so a demoted symbol whose semantic entry survived in `data/function_patterns.json` still resolved and still got hooked — failing *open*. Since 2026-09-17 the codegen is fail-closed — a non-`ok` symbol gets its address constant (a `va` global IS an address) but no `_Pattern` constant, no typed `engine::` accessor and no event-hook row, so a use site becomes a compile error instead of a silent mis-resolve (`tests/test_symbols.py::test_codegen_is_fail_closed_on_non_ok_status`). `scripts/sync_symbol_patterns.py` now prunes non-ok entries, and `rsmm.engine.symbols.validate()` fails when a non-ok symbol still has a pattern (so `rsmm symbols` catches it in CI without the exe). `validate()` also rejects two `status=ok` names on one address unless both notes say `SAME FUNCTION as <other>` — an unacknowledged alias strands one of the pair on the next remap.

**Loader memory safety is one function, not six.** `src/loader/include/mem_safe.h` (`rsmm::mem_accessible` / `mem_readable` / `mem_load` / `mem_read_cstr`) is the only page-state guard. Every detour reads game memory at RE-derived offsets; MinGW has no `__try/__except`, so an unguarded read on a stale offset is a hard crash of the whole game. Never hand-roll another `readable()` — the five copies that existed had each drifted (missing protection-bit checks, missing wrap guards, a `need_write` branch with an empty body). Generated payload decoders go through it too (`cmd_symbols.py::_guarded_decl`).

**Loader log lines carry a severity, and it is earned.** `Loader::log_err` / `log_warn` (loader.h) prefix a `[err]`/`[warn]` token **before** the subsystem tag — `[ts sid pid] [err] [ui-hook] resolve failed` — so `[subsystem]` stays exactly where every existing reader looks for it. Both parsers consume severity then tag (`cmd_log.line_severity` / `_style_line`, `apps/desktop/src/lib/loader-log.ts`), and `rsmm log --errors` + the desktop "problems only" filter are built on it. The rule that keeps it useful: a capability that is off because the user did not arm it (`RSMM_ENABLE_*` unset), or because no mod registered content for it, is plain `log()`. Tagging those as errors reproduces the undifferentiated wall the severity exists to cut through — roughly a third of the lines matching /fail|disabled/ are exactly that case. A change here needs a loader publish (`gh workflow run publish-loader.yml`) to reach users; the parsers tolerate untagged lines, so an old DLL with a new app is degraded, not broken.
**Boot canary.** `src/loader/src/health.cpp` opens `<game>/mods/_health.json` before any mod code runs and stamps `per_mod:<id>` as each `init.lua` executes; it closes ~2 s after `ready`. A canary still open at the next launch means the previous run died at that step, so the crash is attributed to that mod. Three consecutive failed boots → the mod is skipped at load (a mod that bricks startup can't be turned off from inside the game). Any successful boot resets the counters. Backs `R.health`.

`<game>/mods/_health.json` is the ONE health file and the loader owns it — the canary lives *inside* it as a `canary` node, not beside it. `rsmm.sdk.health` is the CLI's read/write side and must address that file and that schema (`canary.step`, `mods.<id>.disabled`). It used to address `<cooking>/.rsmm_health.json` + `.rsmm_boot.json` with `last_step`/`disabled_by_health`, which nothing has ever written: `rsmm doctor` reported "no crash records" while a mod sat disabled, `apply`'s quarantine pass never quarantined, `safe-mode --bisect` wrote where the loader would never read, and the post-game-update reset cleared the wrong file — four silent no-ops from one wrong path. CLI writes are read-modify-write on the whole document so they cannot drop the canary node the loader is mid-way through keeping.

**The event catalog is mined, not hand-written.** `data/symbols.json`'s `gameplay_event_catalog` (150 names) comes from `python tools/mine_event_names.py --verify --json …`, which harvests SCREAMING_CASE literal pools from the shipped exe and keeps only pools anchored by an event name independently confirmed in-game. Do NOT try to find these by scanning `.text` for `lea reg, [rip+str]` — the engine builds an event id from the name's CRC and stores the pointer in a table, so a reference scan finds ~none of them (an early version of the miner did exactly this and reported 0/6 anchors). Clustering is the signal. Regenerate after a game patch and re-run with `--verify`; `rsmm symbols gen` emits `src/loader/lib/events_gen.lua` from it, which backs `R.events.known()`.

**Event payloads are decoded by VFTABLE, not by name.** `tools/mine_event_payloads.py` walks MSVC RTTI (type descriptor → complete object locator → vftable), finds the code storing each vftable, and records the `[this+disp]` writes *within .pdata function bounds* — giving offsets + widths for the ~24 `oCGameNamedEvent` subclasses that carry data (every other event name is dispatched as the bare base class: header only). Three traps, all hit once: (1) walk a fixed byte window instead of the `.pdata` range and the base class comes back with 32 phantom "fields" out to +0x238; (2) take the union of writes across all sites and the base class inherits every subclass's fields — the miner drops classes by construction-site count (>30 = base); (3) *majority* vote instead of union loses the fields the EMITTER writes after construction (the give path writes the MO GUID itself), so both confirmed layouts vanish. `--verify` asserts the hand-RE'd `NETWORK_DAMAGE` / `GIVE_MAGICAL_OBJECT` offsets survive a re-mine. Offsets/widths are recovered; MEANING is not — field names are mechanical (`u50`) unless hand-confirmed. Schemas live in `data/symbols.json::event_payload_schemas`, generate `src/loader/src/event_fields.gen.h`, and the decode is gated on `va_globals_trusted` (vftable RVAs are build-specific).

**Hook signatures carry ABI shape.** `hook_lua.cpp`'s detour table is indexed by `[shape][slot]`, where shape encodes which of the first four args are floating-point plus whether the return is — the Windows x64 ABI picks RCX/RDX/R8/R9 vs XMM0-3 *by argument type*, so one all-integer prototype cannot serve a float-taking function. `fn_call.cpp` does the same over 3^4 arg shapes x 3 return classes. Convention shared by both: a slot holds the RAW register bits, so `'f'` is the float's 32 bits in the LOW half (not a widened double).

**The loader DLL and Lua SDK ship out of band, like the pattern DB.** `winhttp.dll` and `src/loader/lib|lua/*.lua` are bundled into the PyInstaller sidecar, which is bundled into the Tauri app — so before `rsmm update-loader` existed, a one-line `rsmm.lua` change cost a full desktop release *and* a reinstall on every user's machine, even though the SDK is disk-loaded and a file copy would have done it. `rsmm.engine.loader_update` is `data_update` one tier up: a rolling `loader` GitHub release carries a **signed** manifest + `loader-bundle.tar.gz`, published by `scripts/publish_loader.sh`. The Python CLI and desktop UI stay on the Tauri updater — they are the things doing the planting. Four rules hold it together:

1. **Verification is mandatory and fail-closed.** This channel plants code that gets injected into the game process. The manifest is signed with the *same* minisign key as the desktop bundles (pubkey duplicated into `loader_update.PUBLIC_KEY` because `tauri.conf.json` is not in the frozen bundle; a test asserts they stay equal) and hashes every payload file, so signing the manifest signs the bundle. There is no unsigned path, no hash-only fallback, no override flag — `rsmm.engine.minisign` is a pure-stdlib Ed25519 *verifier* only, because the runtime CLI declares no dependencies.
2. **Destinations are an allowlist, not a hint.** `resolve_destination()` maps exactly `winhttp.dll` → `<game>/` and `lib/**` → `<game>/rsmm/lib/`; anything else aborts the whole update. Members are read and written one at a time rather than via `extractall`, so symlinks/hardlinks/devices/traversal are rejected rather than merely unlikely.
3. **`abi` is the compat valve.** When a loader change also needs new *planting* logic CLI-side, bump `abi`; older CLIs then report `needs_app_update` instead of planting a payload they don't understand.
4. **`data/loader_version.json` is what stops a downgrade.** `restore --all` wipes the loader and `install-loader` replants the copy bundled in *this* build — which would silently roll back anyone ahead via the channel. So `apply_update` caches the verified payload in `<game>/rsmm/cache/loader/`, and `install_loader.py::_replant_newer_loader` re-plants it (re-verifying the signature: the game dir is not a trusted store) when its version exceeds the bundled stamp. An uncommitted version bump breaks this silently in both directions.

5. **A plant is all-or-nothing, and serialised.** Every destination is probed for writability *before* the first byte is written (`_preflight_writable`), so the overwhelmingly common failure — Ravenswatch is running and holds `winhttp.dll` open — plants nothing at all and says "close Ravenswatch". Planting the SDK and only then discovering the lock leaves a new SDK calling into an old DLL, which is a runtime error inside every mod. The DLL is still written last as a backstop, staging files are PID-qualified (a shared `.rsmm-new` name means one process's `os.replace` eats another's file), and an `O_CREAT|O_EXCL` lock under `<game>/rsmm/` serialises concurrent updates — the desktop's launch check racing a hand-run CLI is routine. The planted manifest is stamped only after every file lands, so an interrupted update reads as the old version and is simply redone.

Two env overrides exist for tests and dev checkouts — `RSMM_LOADER_UPDATE_PUBKEY` and `file://` bases — and **both are refused in a frozen build**, which is what every user runs: an env var that swaps the trust root is an env var that installs an arbitrary DLL into the game process. Before the first publish the assets legitimately 404; that is reported as `not_published`, not as an error, so builds shipped ahead of the channel do not nag on every launch.
