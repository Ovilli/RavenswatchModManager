# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository shape

Hybrid monorepo with two parallel toolchains:

- **Python CLI** (`src/rsmm/`, entry point `./rsmm` at repo root) — all mod install / lifecycle logic. Stdlib-only at runtime (`pyproject.toml` declares no `dependencies`). Installed editable via `pip install -e .`.
- **TypeScript pnpm workspace** (`apps/*` + `packages/*`) — Tauri 2 desktop shell, Hono API, Next.js site, Astro docs, shared `@rsmm/*` packages. Orchestrated by Turbo (`turbo.json`).
- **Native loader DLL** (`src/loader/`, Windows-only) — `winhttp.dll` proxy + MinHook + Lua 5.4 VM injected into Ravenswatch for Lua-scripted mods. Built with CMake. Texture/asset overrides work without it. The Lua SDK (`src/loader/lib/rsmm.lua` + the generated `engine_gen.lua`/`events_gen.lua`, plus the `src/loader/lua/rsmm/*.lua` submodules it requires) is **disk-loaded from `<game>/rsmm/lib/`, not embedded in the DLL** — a Lua-only change ships via `rsmm install-loader` (or a straight file copy), no rebuild.

The desktop app does **not** reimplement the CLI — it bundles the Python CLI as a PyInstaller sidecar (`apps/desktop/src-tauri/binaries/rsmm-<triple>[.exe]`) and shells out via Tauri's `shell:allow-execute`. See `scripts/build-sidecar.py` for the bundle definition (every data file the frozen CLI needs must be in `add_data_args` or it will crash on a fresh user install).

## New-capability workflow

Applies to any subsystem with no `status="ok"` symbol in `data/symbols.json` yet. Capability classes that already have a dedicated miner — event names (`tools/mine_event_names.py`), event payloads (`tools/mine_event_payloads.py`), vtable interface methods (`tools/mine_vtable_interfaces.py`), class ids (`tools/mine_class_ids.py`) — skip to step 5; for those the mining IS the recon.

1. **Check the map before doing any RE.** `rsmm symbols list` / `rsmm symbols resolve <Name>`, and grep the `note` prose in `data/symbols.json` — 191 symbols, most carrying a paragraph of hand-RE, including the ones that were tried and shelved. `docs/SYMBOLS.md` and `apps/docs/.../reference/symbols.md` are the same map rendered. A "new" subsystem is often one `unverified` entry away from working.
2. **Static recon anchored to a symbol you already trust**, never a cold read of an isolated function that looks like the right thing. `scripts/disasm.py --resolve <Name>` lands inside a known function, `--calls <Name>` lists its callees, `--whatis <va>` names whatever you drifted into. `tools/symbol_locate.py` exists because the opposite approach produced confident wrong answers: scoring every function in the corpus handed `Netcode_DropPeer` its *caller* (the note's quoted string is logged one frame up) and gave three unrelated symbols the same 1234-line level-load orchestrator. Constrain to a handful of candidates first (vftable class+slot; callers/callees of an already-located symbol; the functions called *next to* a string's use), then discriminate inside that pool only.
3. **Dynamic proof against a known-good trigger is a gate, not a formality — it comes before any code is written.** Static reading gets the shape; only the running game gets the address. Launch with `RSMM_DUMP_SYMBOLS=1` in the loader flags and diff the result with `rsmm symbols audit`, which flags any `status=ok` symbol the loader resolved to null or to non-prologue bytes. For a struct, walk a live instance with `R.debug.dump` / `R.debug.find_arrays` / `R.debug.strings`, which turn multi-launch struct-hunting into one launch. Native `read_*` is page-guarded so probing is free — but the moment a probed pointer becomes a call argument the engine owns the deref, so validate with `R.ptr.*` and call through `R.engine.call_safe`.
4. **Look for the second gate before declaring victory** — verify the end-to-end effect, not that the call fired. Canonical case: POIs. A mod tiledef needs a sibling `.UsedRscCache.ot` or it is registered and never placed; fixing every per-tile cache still left the POI invisible for another playtest, because the *mapdef's own* cache gates its pool one-for-one. Both gates fail silently and neither logs anything, so "the tile registered" proved nothing.
5. **Only then write the symbol entry, regen, and build the SDK-side capability.** `status` is not a label you pick: `rsmm symbols check` fails an `ok` whose pattern is absent from `data/function_patterns.json`, so `ok` is *earned* by `scripts/gen_function_patterns.py` → `scripts/sync_symbol_patterns.py`; follow with `rsmm symbols gen` and `python scripts/verify_symbol_resolve.py`. If the symbol was found by a hand-derived anchor (vftable class+slot, a callgraph neighbour, a quoted string), record it as a structured `locator` — `tools/backfill_locators.py --apply`, and `--check` asserts it still resolves — because that is what stops the next game patch from being another manual session. The deliverable is a kind builder, an engine cooker, or an `R.*` API, never a bespoke script: `rsmm lint` fails any `*.py` in a mod that isn't `on_disable.py`, and ERRORs on a literal `0x14xxxxxxx` or on `_internal`/`peek`/`poke`/`read_*`/`write_*`/`call_raw`/`engine.resolve` in mod Lua. For a content kind, set an honest `KIND_CONFIDENCE` rating — anything below `confirmed` forces `sdk.Mod(..., experimental=True)`.
6. **Park ruled-out hypotheses as `unverified` entries with the reasoning in `note`** (the field is `note`, singular). A hypothesis that cost a session to eliminate is worth as much as one that worked, and only the map remembers it. `LobbyMembers_List` is the shape to copy — full member layout, then "⚠ The caller OWNS the returned members and destroys each one … The damage meter does not need to", so the next session reads why not to call it instead of re-deriving it. Parking is safe by construction: `validate()` fails a non-`ok` symbol that still has a pattern in the DB, so an `unverified` entry cannot be resolved or hooked by the loader.

## Architecture notes worth knowing up front

**Asset application is install-time file replacement, not runtime patching.** Ravenswatch loads cooked assets from `<install>/DarkTalesResources/_Cooking/<encoded>` where `<encoded>` is the plaintext path run through a fixed Caesar cipher (`src/rsmm/engine/cipher.py`, `src/rsmm/engine/find_iyg.py`). `apply_mods.py` walks `mods/`, resolves decoded → encoded via `data/asset_map.json`, backs the original up as `<file>.rsmm.bak`, and copies the override into place. State lives in `<install>/DarkTalesResources/_Cooking/.rsmm_state.json`. Removing the manager is `./rsmm restore --all`. The engine accepts any byte-compatible file — no checksums, no signatures. This avoids the anti-tamper logic in `Ravenswatch.exe`; full background in `apps/docs/src/content/docs/architecture/overview.md`.

**Sound banks are the one asset family NOT in `asset_map.json`.** Everything else is loaded through `UsedRscList.ot`, and `asset_map.json` is derived from that list — but the engine loads `Audio/<Name>.bank` by path, so those 16 files never appear in the manifest and every `dec2enc` lookup misses. `apply_mods.resolve_audio_bank()` handles them by ciphering the plaintext path straight through (the `!` directory-collapse rule that complicates normal cooked paths does not apply at that depth: `Audio/Music.bank` → `Wwtdr\Hwvdb.agzm`), and it is wired into `resolve_special` so overriding a bank works like any other asset. The mirroring script needs the same special case — `extract_uncooked.audio_pairs()` lists the cooked audio dir and deciphers each name back, because a CSV-only walk mirrors zero audio. Only the bankset descriptor (`Audio/DarkTales.bankset.FModEventProject.gen`) IS in the map, so `audio_pairs` skips it. Banks are containers: `scripts/extract_audio.py` walks the embedded FSB5 sub-banks (mode 15 Vorbis, setup headers stripped by FMOD and rebuilt by `python-fsb5` — plain ffmpeg cannot read them) and writes one file per sample.

**`*.UsedRscCache.ot` is the second family outside `asset_map.json`, and it is load-bearing.** A definition's resource cache is a plaintext preload manifest sitting beside it — one line per resource, `<Root>|<Decoded\\Path>|<oCClass>` — holding that definition's full transitive dependency closure (the Dark Hills start tile: 784 lines). The engine finds it **by convention, never through `UsedRscList.ot`**: `sub_140311110` appends the literal `.UsedRscCache.ot` to the resource name and applies the usual `\\`→`!` collapse. So none of the 575 shipped caches has a manifest record, none is in `asset_map.json`, and `extract_uncooked.py` mirrored zero of them until `cache_pairs()` was added — the same blind spot as the sound banks. **237 of 237 tiledefs have one, no exceptions** (also 105 hero/enemy `entity`, 81 `enemydef`, … — but 0 of 370 levels and 0 of 733 scenery props). Two failure modes, both hit in-game: a new tiledef with *no* cache preloads nothing, so it is registered, never placed, and reports nothing — that, not the mapdef pool, is why POIs never appeared; and a *stale* cache (a `replace_base` edit reaching assets the cache never listed) leaves a null in the preloaded pointer vector, which the teardown loop at `0x140476f60` destroys without a null check, faulting at `0x1401273b6` reading address 0 with no connection to the real mistake. **It gates at two levels**: the mapdef has a cache of its own listing its pool's tiledefs ONE FOR ONE (Dark Hills: 77 pool entries, 77 `|oCDtTileDefinition` lines), so a tile appended to the pool but absent from the map's cache is never loaded and never placed — fixing only the per-tile caches left the POI invisible for another playtest. The invariant to hold is `pool == map cache tiledef lines`. `rsmm.engine.rsc_cache` builds them, append-only on purpose (a surplus line wastes a preload; a missing one crashes the game), and `_merge_rsc_cache` unions them across mods for the same reason `_merge_map_pool` exists. Two rules: a cache must **not** be registered in `UsedRscList.ot` (`plan_apply` skips them), and anything asking "does the game ship this path" must exempt them, because `is_vanilla_encoded` is `asset_map`-backed and answers False for every shipped cache. ⚠ `data/symbols.json` calls the destroy thunk at `0x1401273b0` `NamedEvent_Delete`; it has **358 callers** and is the generic `destroy(obj)` vtable thunk — the name is not evidence a crash involves named events.

**Installing a detour is one function, not nine.** `src/loader/include/hook_util.h` (`rsmm::hook_install` by pattern name, `hook_install_at` by address, `resolve_checked` for call-only targets, `hook_remove`) is the only path to `MH_CreateHook`. Nine `hook_*.cpp` files used to hand-roll resolve→verify→create→enable and had drifted: only two checked that the target is a **function entry**, several skipped `fn_verify`, and some ignored `MH_EnableHook` failures. Two invariants it enforces, both of which were being violated in shipped code:

1. **`fn_verify` is not an entry-point check.** It proves the recorded bytes are at the address — which a *mid-function* match also does, because a pattern from an older build keeps matching after the routine is merged into a larger one. Only `.pdata` knows where functions begin, so `fn_is_function_start()` (binary search over the module's exception table) gates every install. A detour on a non-entry-point does not intercept a call, it **corrupts** the function it lands in, and the crash surfaces somewhere unrelated much later. The analytics firehose — armed by default on every install — was detouring 0x8d0 bytes inside an unrelated function; `hook_skins.cpp`'s five targets were wrong the same way (one "vector grow" was an aligned-array *deallocator*), and were relocated on 2026-08-09 — it resolves through `Sym::` now. The two literals left are `hook_skills.cpp` and `hook_spawn.cpp`, which have no pattern in the DB at all, so both capabilities resolve to nothing and disable themselves (`install-loader` prints them on every run).
2. **Never resolve by a `"FUN_<addr>"` literal.** That is an address from whatever build the line was written against. The pattern DB keeps such names alive as legacy aliases, so they resolve *and* verify, and land wherever the old bytes now match. Use `Sym::<Name>_Pattern`; add a symbol to `data/symbols.json` if none exists. `tests/test_loader_hook_hygiene.py` gates both rules in CI (no game exe needed) with a shrink-only allowlist; `scripts/verify_symbol_resolve.py` additionally reports where each remaining literal actually lands.

Mod-supplied addresses (`rsmm.hook` → `hook_lua.cpp`) get `EntryCheck::Warn` instead of a refusal: x64 may legitimately omit a true leaf from `.pdata`, and the mod author owns that risk. `hook_lua` keeps its own create/enable sequence because it must set the slot's `installed` flag *between* the two calls — the other order let the game enter a detour while the flag was false, and the hooked function silently did nothing on its first call.

**Demoting a symbol is only real once its pattern is gone.** `status` alone is cosmetic: the C++/Lua codegen does not filter by it, so a demoted symbol whose semantic entry survives in `data/function_patterns.json` still resolves and still gets hooked — failing *open*. `scripts/sync_symbol_patterns.py` now prunes non-ok entries, and `rsmm.engine.symbols.validate()` fails when a non-ok symbol still has a pattern (so `rsmm symbols` catches it in CI without the exe). `validate()` also rejects two `status=ok` names on one address unless both notes say `SAME FUNCTION as <other>` — an unacknowledged alias strands one of the pair on the next remap.

**Loader memory safety is one function, not six.** `src/loader/include/mem_safe.h` (`rsmm::mem_accessible` / `mem_readable` / `mem_load` / `mem_read_cstr`) is the only page-state guard. Every detour reads game memory at RE-derived offsets; MinGW has no `__try/__except`, so an unguarded read on a stale offset is a hard crash of the whole game. Never hand-roll another `readable()` — the five copies that existed had each drifted (missing protection-bit checks, missing wrap guards, a `need_write` branch with an empty body). Generated payload decoders go through it too (`cmd_symbols.py::_guarded_decl`).

**Loader log lines carry a severity, and it is earned.** `Loader::log_err` / `log_warn` (loader.h) prefix a `[err]`/`[warn]` token **before** the subsystem tag — `[ts sid pid] [err] [ui-hook] resolve failed` — so `[subsystem]` stays exactly where every existing reader looks for it. Both parsers consume severity then tag (`cmd_log.line_severity` / `_style_line`, `apps/desktop/src/lib/loader-log.ts`), and `rsmm log --errors` + the desktop "problems only" filter are built on it. The rule that keeps it useful: a capability that is off because the user did not arm it (`RSMM_ENABLE_*` unset), or because no mod registered content for it, is plain `log()`. Tagging those as errors reproduces the undifferentiated wall the severity exists to cut through — roughly a third of the lines matching /fail|disabled/ are exactly that case. A change here needs a loader publish (`gh workflow run publish-loader.yml`) to reach users; the parsers tolerate untagged lines, so an old DLL with a new app is degraded, not broken.

**The desktop Log screen does not poll through the sidecar.** Discovery does — the CLI owns game-dir resolution, archived-run lookup (`loader-runs` / `loader-log --run`) and session slicing for the first page, and returns the file's `bytes` — but following is `read_loader_log_chunk` in `apps/desktop/src-tauri/src/loader_log.rs`, which seeks to a byte offset and returns complete lines only. The old loop spawned a PyInstaller process every second (a cold start plus an AV scan of the unpacked bundle, on Windows) to re-read the whole file. Three invariants: the returned offset is always a line boundary (so a chunk can never split a line *or* a UTF-8 sequence); a shrunk file sets `reset`, and the frontend REPLACES its buffer rather than splicing two runs into one apparent session; and the command only reads `mods/_log*.txt` and `rsmm/logs/*.log`, judged on the canonicalised path. The poll is also gated on `document.visibilityState`. Archived-run names come from the UI and are resolved by `cmd_log.resolve_run` against the archive LISTING, never joined onto a directory.

**Boot canary.** `src/loader/src/health.cpp` opens `<game>/mods/_health.json` before any mod code runs and stamps `per_mod:<id>` as each `init.lua` executes; it closes ~2 s after `ready`. A canary still open at the next launch means the previous run died at that step, so the crash is attributed to that mod. Three consecutive failed boots → the mod is skipped at load (a mod that bricks startup can't be turned off from inside the game). Any successful boot resets the counters. Backs `R.health`.

`<game>/mods/_health.json` is the ONE health file and the loader owns it — the canary lives *inside* it as a `canary` node, not beside it. `rsmm.sdk.health` is the CLI's read/write side and must address that file and that schema (`canary.step`, `mods.<id>.disabled`). It used to address `<cooking>/.rsmm_health.json` + `.rsmm_boot.json` with `last_step`/`disabled_by_health`, which nothing has ever written: `rsmm doctor` reported "no crash records" while a mod sat disabled, `apply`'s quarantine pass never quarantined, `safe-mode --bisect` wrote where the loader would never read, and the post-game-update reset cleared the wrong file — four silent no-ops from one wrong path. CLI writes are read-modify-write on the whole document so they cannot drop the canary node the loader is mid-way through keeping.

**The event catalog is mined, not hand-written.** `data/symbols.json`'s `gameplay_event_catalog` (150 names) comes from `python tools/mine_event_names.py --verify --json …`, which harvests SCREAMING_CASE literal pools from the shipped exe and keeps only pools anchored by an event name independently confirmed in-game. Do NOT try to find these by scanning `.text` for `lea reg, [rip+str]` — the engine builds an event id from the name's CRC and stores the pointer in a table, so a reference scan finds ~none of them (an early version of the miner did exactly this and reported 0/6 anchors). Clustering is the signal. Regenerate after a game patch and re-run with `--verify`; `rsmm symbols gen` emits `src/loader/lib/events_gen.lua` from it, which backs `R.events.known()`.

**Event payloads are decoded by VFTABLE, not by name.** `tools/mine_event_payloads.py` walks MSVC RTTI (type descriptor → complete object locator → vftable), finds the code storing each vftable, and records the `[this+disp]` writes *within .pdata function bounds* — giving offsets + widths for the ~24 `oCGameNamedEvent` subclasses that carry data (every other event name is dispatched as the bare base class: header only). Three traps, all hit once: (1) walk a fixed byte window instead of the `.pdata` range and the base class comes back with 32 phantom "fields" out to +0x238; (2) take the union of writes across all sites and the base class inherits every subclass's fields — the miner drops classes by construction-site count (>30 = base); (3) *majority* vote instead of union loses the fields the EMITTER writes after construction (the give path writes the MO GUID itself), so both confirmed layouts vanish. `--verify` asserts the hand-RE'd `NETWORK_DAMAGE` / `GIVE_MAGICAL_OBJECT` offsets survive a re-mine. Offsets/widths are recovered; MEANING is not — field names are mechanical (`u50`) unless hand-confirmed. Schemas live in `data/symbols.json::event_payload_schemas`, generate `src/loader/src/event_fields.gen.h`, and the decode is gated on `va_globals_trusted` (vftable RVAs are build-specific).

**Hook signatures carry ABI shape.** `hook_lua.cpp`'s detour table is indexed by `[shape][slot]`, where shape encodes which of the first four args are floating-point plus whether the return is — the Windows x64 ABI picks RCX/RDX/R8/R9 vs XMM0-3 *by argument type*, so one all-integer prototype cannot serve a float-taking function. `fn_call.cpp` does the same over 3^4 arg shapes x 3 return classes. Convention shared by both: a slot holds the RAW register bits, so `'f'` is the float's 32 bits in the LOW half (not a widened double).

**The loader DLL and Lua SDK ship out of band, like the pattern DB.** `winhttp.dll` and `src/loader/lib|lua/*.lua` are bundled into the PyInstaller sidecar, which is bundled into the Tauri app — so before `rsmm update-loader` existed, a one-line `rsmm.lua` change cost a full desktop release *and* a reinstall on every user's machine, even though the SDK is disk-loaded and a file copy would have done it. `rsmm.engine.loader_update` is `data_update` one tier up: a rolling `loader` GitHub release carries a **signed** manifest + `loader-bundle.tar.gz`, published by `scripts/publish_loader.sh`. The Python CLI and desktop UI stay on the Tauri updater — they are the things doing the planting. Four rules hold it together:

1. **Verification is mandatory and fail-closed.** This channel plants code that gets injected into the game process. The manifest is signed with the *same* minisign key as the desktop bundles (pubkey duplicated into `loader_update.PUBLIC_KEY` because `tauri.conf.json` is not in the frozen bundle; a test asserts they stay equal) and hashes every payload file, so signing the manifest signs the bundle. There is no unsigned path, no hash-only fallback, no override flag — `rsmm.engine.minisign` is a pure-stdlib Ed25519 *verifier* only, because the runtime CLI declares no dependencies.
2. **Destinations are an allowlist, not a hint.** `resolve_destination()` maps exactly `winhttp.dll` → `<game>/` and `lib/**` → `<game>/rsmm/lib/`; anything else aborts the whole update. Members are read and written one at a time rather than via `extractall`, so symlinks/hardlinks/devices/traversal are rejected rather than merely unlikely.
3. **`abi` is the compat valve.** When a loader change also needs new *planting* logic CLI-side, bump `abi`; older CLIs then report `needs_app_update` instead of planting a payload they don't understand.
4. **`data/loader_version.json` is what stops a downgrade.** `restore --all` wipes the loader and `install-loader` replants the copy bundled in *this* build — which would silently roll back anyone ahead via the channel. So `apply_update` caches the verified payload in `<game>/rsmm/cache/loader/`, and `install_loader.py::_replant_newer_loader` re-plants it (re-verifying the signature: the game dir is not a trusted store) when its version exceeds the bundled stamp. An uncommitted version bump breaks this silently in both directions.

5. **A plant is all-or-nothing, and serialised.** Every destination is probed for writability *before* the first byte is written (`_preflight_writable`), so the overwhelmingly common failure — Ravenswatch is running and holds `winhttp.dll` open — plants nothing at all and says "close Ravenswatch". Planting the SDK and only then discovering the lock leaves a new SDK calling into an old DLL, which is a runtime error inside every mod. The DLL is still written last as a backstop, staging files are PID-qualified (a shared `.rsmm-new` name means one process's `os.replace` eats another's file), and an `O_CREAT|O_EXCL` lock under `<game>/rsmm/` serialises concurrent updates — the desktop's launch check racing a hand-run CLI is routine. The planted manifest is stamped only after every file lands, so an interrupted update reads as the old version and is simply redone.

Two env overrides exist for tests and dev checkouts — `RSMM_LOADER_UPDATE_PUBKEY` and `file://` bases — and **both are refused in a frozen build**, which is what every user runs: an env var that swaps the trust root is an env var that installs an arbitrary DLL into the game process. Before the first publish the assets legitimately 404; that is reported as `not_published`, not as an error, so builds shipped ahead of the channel do not nag on every launch.

**Path resolution in frozen mode.** `src/rsmm/engine/paths.py::_find_repo_root` resolves `REPO_ROOT` to PyInstaller's `_MEIPASS` when `sys.frozen` is set. Anything bundled in `build-sidecar.py`'s `add_data_args` is reachable at the same relative path it had in source; anything not bundled is silently missing at runtime. `DEFAULT_GAME_DIR` and `MODS_DIR` are PEP 562 lazy attrs — importing `rsmm.engine.paths` does *not* trigger the disk scan for Ravenswatch (slow on Windows with network drives).

**Re-invoking the CLI from itself uses `self_cmd()`** (`engine/paths.py`). In a frozen bundle `sys.executable` IS rsmm; in source mode it's the Python interpreter + the wrapper script. Never hardcode the entry point.

**Subcommand dispatch is dynamic** (`src/rsmm/cli/_dispatch.py`). Modules are loaded with `importlib`. PyInstaller can't see them statically — CI uses `--collect-submodules=rsmm.cli` etc., the local builder uses an explicit `HIDDEN_IMPORTS` list. Adding a new subcommand requires no edits to bundling if `--collect-submodules` covers it, but **does** require adding the module to `LEGACY` (or argparse subparsers) in `_dispatch.py`.

**Terminal UI lives in three primitives, not in each command.** `src/rsmm/cli/_term.py` (colour via `Style()`, panels, rules, bars, width/height, `visible_len`/`truncate`), `_keys.py` (raw mode, SGR mouse 1006 + motion 1003 for hover, alternate screen, `read_key()` → `UP`/`DOWN`/`ENTER`/`WHEEL_UP`/`MOTION`/`click`/…), `_clip.py` (clipboard). Never hand-roll ANSI in a command module. `Style()` decides colour once from the stream (`NO_COLOR` / `FORCE_COLOR` / isatty), so piping any command yields clean text — verify that with `grep -c $'\033'` on redirected output when touching a command's rendering. Two recurring traps: **pad the plain string before styling** (`f"{name:<20}"` on a styled string counts the escape bytes as width and mis-aligns every coloured row — that's what `visible_len` is for), and **Python 3.11 forbids backslash escapes inside f-string expressions**, so hoist glyphs like `›`/`↵`/`·` to module constants.

Bare `rsmm` at an interactive terminal opens the home screen (`cmd_shell.py`, also `rsmm home`); piped or redirected it still prints help, so scripts and the desktop sidecar are unaffected. It draws on the **alternate screen buffer** — without that every redraw is appended to scrollback and the terminal grows for the whole session. `home` is deliberately distinct from `menu`, which is the *in-game* mod menu. The home screen owns no logic: it shells back into the real subcommands, and its Mods screen reads state through `cmd_mods._states()` — which parses the aligned `enabled     = true` form the manifests actually ship, so a naive `"enabled = true" in text` check reports every mod as disabled.

**Desktop UI text is translated by SOURCE STRING, not by key.** `apps/desktop/src/lib/i18n.ts` looks the English sentence itself up in the active locale's catalog (`src/locales/<tag>.ts`) and returns the English back when there is no entry — a gettext-shaped retrofit of an app that was written English-only, so an unmigrated component still renders and a stale translation degrades to English rather than to a raw `settings.paths.title` on screen. The upkeep cost that choice creates (a reworded English string silently orphans its translation) is paid by `src/locales/coverage.test.ts`, which extracts every `t(…)`/`tr(…)`/`msg(…)`/`t.n(…)` literal from the source tree and fails on a missing entry, an entry nothing renders, or a `{placeholder}` that changed between source and translation — plus a GLOSSARY table (profile 方案, overlay 悬浮窗, loader 加载器, mod 模组, …) that fails when a term drifts between panels, which is the failure mode a source-keyed catalog invites: `profile` rendered 配置 in one place and 方案 in another, beside a mod's own `config` which IS 配置. Four rules: components take `t` from `useT()` (subscribed to `settings.language`, which is what makes switching instant); plain modules use the module-level `t`/`tr`, kept in sync by the single `setLocale` subscription in `main.tsx`; a string declared at module scope (a nav table, a settings tab) is wrapped in `msg()` and translated at its render site; and a sentence carrying markup mid-way stays ONE message rendered through `<TParts>` rather than being split into fragments a translator cannot reorder. Deliberately NOT translated: CLI output, mod-supplied copy, and engine strings — and `lib/errors.ts::explainError` matches on the CLI's English text, so translating `rsmm.ts`'s error messages would silently break every actionable headline in the app. `applyAppearance` is still the single writer of the font vars and now also stamps `<html lang>` and appends a CJK fallback stack for a CJK locale.

**Desktop ↔ CLI bridge.** Frontend calls Tauri's `Command` API to spawn the sidecar; responses come back as JSON via `rsmm.cli.json_bridge`. CSP in `apps/desktop/src-tauri/tauri.conf.json` whitelists `connect-src` for outbound API calls — if you add a new backend domain, add it there or fetches fail silently. API CORS in `apps/api/src/env.ts::trustedOrigins` must include every Tauri origin the desktop ships under; missing `http://tauri.localhost` (Windows WebView2) silently breaks every store fetch.

**Linux installs the updater cannot write to have an escape hatch, not a dead end.** Tauri's updater only rewrites the *running* binary, so a `.deb` (root-owned `/usr/bin`, `$APPIMAGE` unset) and a root-owned AppImage store (`/opt`, AppImageLauncher) can never update in place — that was a manual reinstall on every release. `update_env.rs` detects it up front (the plugin otherwise only reports `Permission denied (os error 13)` *after* a full download) and `update_migrate.rs` plants a self-updating copy: the pending update is fetched through `Update::download()` so the **minisign signature is verified by the same code path and pubkey as any other update** — there is no unsigned path — then checked for the AppImage type-2 marker, staged PID-qualified, `chmod 0755`, renamed to `~/Applications/RavenswatchModManager.AppImage`. The system `.desktop` entry is located by matching `Exec=` against the running binary (never by guessing the bundler's file name) and re-written into `~/.local/share/applications` under the **same basename**, which shadows `/usr/share/applications` — so the user's existing launcher icon starts opening the AppImage, and `Name`/`Icon`/`StartupWMClass`/`x-scheme-handler/rsmm` (the OAuth deep link) all survive. Two rules: nothing outside `$HOME` is ever touched (the old system copy is the package manager's to remove; the UI just reports the `apt remove` line), and the relaunch is **queued on a 2 s delay and the app quits through `quitApp()`** — starting the new process first hands its argv to `tauri-plugin-single-instance` in the dying instance and the new copy exits immediately. After one migration `$APPIMAGE` is set and the ordinary updater takes over forever.

**Updater + signing.** Tauri updater feed is `https://github.com/Ovilli/RavenswatchModManager/releases/latest/download/latest.json`, assembled by the `publish-updater-manifest` job in `.github/workflows/release.yml` from `.sig` files produced by `pnpm tauri build`. Pubkey embedded in `tauri.conf.json`; signing private key lives in `TAURI_SIGNING_PRIVATE_KEY` repo secret. The job is skipped when `vars.HAS_UPDATER_SIGNING != 'true'`, in which case releases ship without auto-update support.

**Version sources.** Four files must move in lockstep on every release: `apps/desktop/src-tauri/tauri.conf.json`, `apps/desktop/src-tauri/Cargo.toml`, `apps/desktop/src-tauri/Cargo.lock` (the `rsmm-desktop` entry), `apps/desktop/package.json`. Root `package.json` and `pyproject.toml` stay at `0.1.0` — they are not user-facing release versions. Use `scripts/bump-version.py` to keep them aligned. Add a matching entry at the top of `data/changelog.json` in the same commit — the desktop app shows it once in a "What's new" dialog after the updater restarts the user into the new build, and a release with no entry silently shows nothing.

**Release notes ship out of band, like the loader and the pattern DB.** `data/changelog.json` is the single source: the desktop bundle imports it as the offline fallback (`apps/desktop/src/lib/changelog.ts`), `build-sidecar.py` bundles it for `rsmm changelog`, and `scripts/publish_changelog.sh` uploads that exact file to the rolling `changelog` GitHub release — so notes cannot drift between the three. This exists because notes compiled into the app can only reach a user by shipping a build, which is backwards for the thing most in need of announcing: a loader/SDK fix that reaches users through `update-loader` with no app release at all. `rsmm.engine.changelog_feed` degrades fetch → cache (6 h TTL) → bundled copy → `unavailable`, so it is cheap to call every launch and works offline. Unsigned **by design** — display text, never code, never written where the game or loader reads — so the trust model is bounds instead of signatures: every field is type-checked, length-capped and control-character stripped (an ANSI escape in a highlight would repaint the terminal rendering it), and entry/highlight counts are capped. The publish script re-runs the client parser and **refuses to publish if any entry would be dropped**, because a silently-dropped entry is a note nobody will ever see. The dialog also clamps to the running app version: the feed routinely describes a release newer than the binary reading it.

**Release flow.** Push a `v*` tag → `.github/workflows/release.yml` builds matrix (`ubuntu-22.04`, `windows-latest` — macOS support dropped; Windows + Linux only), each leg uploads bundles + `.sig` files to a draft GH release, then `publish-updater-manifest` assembles `latest.json`, then `finalize-release` flips the draft to published. Windows leg uses `shell: pwsh` (not bash) because Git Bash's `/usr/bin/link` shadows MSVC's `link.exe` and breaks Rust builds.

**Loader DLL bundling gotcha.** The Windows CI step builds `winhttp.dll` via `src\loader\build.bat` with `continue-on-error: true`, then PyInstaller bundles `dist/winhttp.dll` if it exists. If `build.bat` writes to the wrong path (it did — fixed in 0.1.11), the build "succeeds" but the DLL is missing from every released sidecar and `rsmm doctor` reports "loader DLL not built" on every user install. Always verify `dist/winhttp.dll` exists after the Windows leg.

**Never `vercel env pull` into `apps/api/`.** Vite substitutes `process.env.X` into `apps/api/src/**` at TRANSFORM time from the env files beside the vitest root, so a pulled `apps/api/.env.local` bakes real production credentials into the code under test — `Object.keys(process.env)` shows nothing while a static `process.env.KV_REST_API_URL` returns the live URL, which is what makes it so hard to see. The consequence is not a stale value: it flipped `upstashEnabled` on inside the suite, so `pnpm test` on a developer's machine incremented PRODUCTION rate-limit counters over the network. Setting `envDir` does not fix it (tried, reverted — it does not stop the substitution). The fix is to not have the file: root `.env.local` is what `pnpm api:dev` and `test/setup-env.ts` read, and nothing needs a per-package copy. `vercel link --cwd apps/api` writes one as a side effect, so delete it afterwards.

**Telemetry / rate limiting.** API uses `createRateLimiter` keyed by user-id or `x-forwarded-for`. Trusted origins, secrets, S3 config all live in `apps/api/src/env.ts`. The auth handler at `/api/auth/*` is Better Auth.

**Engine symbol map (Minecraft-style mappings).** `data/symbols.json` is the canonical, human-authored map from semantic names (`MagicalObject_SpawnAllObjects`) to engine functions/globals — the source of truth. The Ghidra DB names, the loader C++ header (`src/loader/include/symbols.gen.h`), and the Python constants (`src/rsmm/engine/_symbols_gen.py`) are all GENERATED from it via `rsmm symbols gen` (CI `--check`s freshness). Resolution forms, most to least version-resilient: `raw` (`FUN_<addr>` whose byte pattern is in `data/function_patterns.json`, so the loader re-scans across game updates), `anchor` (inlined routine = parent pattern + offset), `va` (base-relative absolute for data globals). Each symbol carries a `status`: `ok` (pattern/anchor resolvable now), `va`, or `unverified` (documented in an older corpus, address not re-confirmed — these are skipped by `rsmm symbols ghidra-export` unless `--include-unverified`). Don't hardcode engine addresses in the loader or SDK; add a symbol and reference `Sym::Name` / `ADDR["Name"]`. To stop functions reading as `FUN_xxxxxxxx` in your own Ghidra, run `rsmm symbols ghidra-export` and apply the script (or feed the `--json` table to the Ghidra MCP bridge). Layers generated on top of the map (the Minecraft Forge/Fabric analogs): (1) **callable typed API** — a symbol with a `cabi` (ret + params) gets a typed, pattern-resolved C++ accessor `engine::Name()` (`src/loader/include/symbols_api.gen.h`) so you call named functions instead of casting raw addresses, plus a Lua resolver `engine_gen.lua`; (2) **event bus** — symbols with `kind="event"` + `lua_event` generate the `EventHook` table spliced into `hook_events.cpp` (`event_table.gen.h`); mods subscribe via `R.on("<lua_event>", cb)`, browse with `rsmm symbols events`; (3) **Lua high-level API** — `R.engine.resolve(name)` / `R.engine.call(name, ...)` in `rsmm.lua` resolve by semantic name through the native `_internal.resolve`/`call`; (4) **engine API docs** — `docs/SYMBOLS.md` (Javadoc analog). All six generated artifacts are `rsmm symbols gen --check`'d in CI.

Three symbol-map caveats that CI does NOT catch: (1) `data/function_patterns.json` is **gitignored** (14 MB, game-derived) — regenerate locally via `scripts/gen_function_patterns.py` / `scripts/add_function_patterns.py`; users receive it through `rsmm update-data` from the rolling `pattern-db` GitHub release (publish with `scripts/publish_pattern_db.sh` — must be run by a human, and the running game reads the planted copy at `<game>/rsmm/data/`, not the repo's). (2) `symbols gen --check` validates artifact consistency only, never that an address is CORRECT — after any remap run `scripts/verify_symbol_resolve.py` against the live exe. (3) The C++/Lua codegen does not filter by `status` — to truly disable a broken symbol you must also strip its semantic entry from the pattern DB so the loader fails closed. `data/symbols.json` is serialized with `indent=1`; keep it that way or diffs explode.

**Symbol-correctness is now gated three ways** (built to end the false-ok class): `scripts/verify_symbol_resolve.py` disassembles where each status=ok pattern resolves in the live exe and fails on a non-function-start — and `install-loader` runs it as a fail-closed pre-plant gate on a dev checkout (skips on frozen/no-capstone/no-exe; `--force` overrides). For ground truth from the RUNNING game, launch with the `RSMM_DUMP_SYMBOLS` loader flag → the loader writes `<game>/rsmm/resolved_symbols.json` (name → resolved VA → prologue bytes), then `rsmm symbols audit` flags any status=ok symbol the loader resolved to null or to non-prologue bytes. To inspect any address without Ghidra, `scripts/disasm.py` disassembles the live exe and resolves call targets to semantic names via the pattern DB.

## Conventions

- **Mods ship data, not code. A discovery script is never the deliverable.** When building a mod, the artifact is a declarative `manifest.toml` (`[[content]]` / `[[patch]]`) plus assets the SDK emits — *not* a bespoke python script. One-off scripts to reverse a byte layout are fine as throwaway *discovery*, but the capability must then graduate into `rsmm.sdk` (a kind builder in `src/rsmm/sdk/kinds/`, an engine cooker in `src/rsmm/engine/`, or the apply pipeline) and the mod re-expressed declaratively; delete the script. `rsmm lint` enforces this — any `*.py` in a mod that isn't a sanctioned lifecycle hook (`on_disable.py`) fails CI. The full custom-magic-item pipeline already lives in the SDK end-to-end (`kinds/item` → `engine/magic_item_cook` → `apply_mods.sync_versiondef`/`sync_usedrsclist`), so a new item = manifest + `rsmm apply`, no script.
- **Mod Lua never touches engine internals directly.** `rsmm lint` ERRORs on literal game VAs (`0x14xxxxxxx`) or low-level primitives (`_internal`, `peek/poke`, `read_*/write_*`, `call_raw`, `engine.resolve`) in any mod's `*.lua`. New capability goes into the SDK (`src/loader/lib/rsmm.lua` + a symbol in `data/symbols.json`); the mod consumes only high-level `R.*`.
- **Never hand a probed or baked pointer to `R.engine.call` without validating the full structure the callee will traverse.** Every loader in-game crash so far was this bug (ctx deref, probe→engine walk). Native `read_*` is page-guarded (bad read → nil, no fault) so probing is safe, but the instant a pointer is a *call argument* the engine owns the deref. Use the pointer-safety library in `rsmm.lua` (`R.ptr.plausible/in_image/has_vtable/vector_valid`) to build the validator and prefer `R.engine.call_safe(name, ptr_arg_specs, ...)` so the guard can't be forgotten. `R.debug.dump(ptr)` / `R.debug.find_arrays(obj)` turn multi-launch struct-hunting into one launch.
- **Some kinds are override-only by design, not by omission.** `reward` and `melody` edit a *retail* def in place (the emitted asset lands at the vanilla decoded path and `apply` backs up + replaces it) rather than cloning under a new id. For `melody` that is forced: the 12 retail melodydefs' `field_a` values are exactly `{0..11}` and `Ui\Melodies` ships exactly 12 icons with no icon ref in the def, so a 13th melody has no index and no icon — the same wall documented for skins and heroes. Don't "fix" these kinds by adding a clone path.
- **Content kinds carry confidence ratings** (`src/rsmm/sdk/content.py::KIND_CONFIDENCE`: confirmed/experimental/guess). Registering a non-confirmed kind raises unless the mod opts in with `sdk.Mod(..., experimental=True)`; lint enforces the manifest flag. When a kind is proven in-game, flip its rating and keep the docs confidence table in sync.
- Commit messages follow `chore(release): bump to 0.1.x + <short reason>` for releases; otherwise free-form imperative. Don't add `Co-Authored-By` lines (see memory).
- Python uses ruff with `line-length=100`, `target-version=py311`. `F401` (unused imports) is intentionally ignored to keep `__init__.py` re-exports clean.
- Biome formats/lints TS. Many paths are excluded (`biome.json` `files.ignore`) including `src/rsmm/**`, `scripts/**`, and generated files — touching those won't lint.
- Tests live in `tests/` (pytest, `testpaths` in `pyproject.toml`). TS tests run under vitest in `@rsmm/schemas`, `@rsmm/api-client`, `apps/desktop` and `apps/www` — `pnpm test:ts` runs those four, `pnpm test` (what CI runs) adds `apps/api`. `apps/www`'s suite is `src/**/*.test.ts` only (plain modules, no jsdom); it exists for `lib/markdown.ts`, whose output reaches `dangerouslySetInnerHTML`. Tests must never mutate tracked `data/` files — an autouse conftest guard fails the offender; `cmd_apply` tests must stub `rsmm.engine.find_iyg.main`.
- **Never `monkeypatch.setattr` `rsmm.engine.paths.MODS_DIR` / `DEFAULT_GAME_DIR`.** They are PEP 562 `__getattr__` attrs, not dict entries: setattr reads the *real* repo `mods/` as the old value and its undo writes that real path into the module dict, permanently shadowing `__getattr__` — even across `importlib.reload`. Every later `RSMM_MODS_DIR` override is then ignored and `rsmm new` scaffolds into the developer's actual `mods/`. Serial-only failure; xdist hides it by splitting the polluter onto another worker. Use `monkeypatch.setenv("RSMM_MODS_DIR"/"RSMM_GAME_DIR", ...)`; `tests/conftest.py::_guard_lazy_paths` and `_guard_real_mods_dir` fail-close on both. `default_game_dir()` reads its override at call time (only the candidate scan, `_scan_game_dir()`, is `@cache`d) — there is no `default_game_dir.cache_clear()`.
